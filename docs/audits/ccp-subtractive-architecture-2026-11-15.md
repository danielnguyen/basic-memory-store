# CCP subtractive architecture audit — BMS

Assessment date: 2026-11-15. Scope: [BMS #71](https://github.com/danielnguyen/basic-memory-store/issues/71). This is a source-based assessment for independent review, not approval to remove code or change deployment.

## Executive recommendation

Keep BMS as the owner-controlled durable memory boundary. First remove demonstrably unused local helpers in a separately authorized change; next establish whether the direct-chat compatibility endpoints have any remaining callers before retiring their orchestration behavior. Do not replace durable memory with a model session, CR runtime state, or an adapter cache. Do not remove storage-side containment because CO and CR also validate policy.

The larger opportunity is to stop maintaining a second chat runtime and to reconcile initiative decision ownership across services. Moving functions into smaller modules would not achieve either outcome. Replacing PostgreSQL/Qdrant or introducing a workflow engine has no demonstrated MVP benefit in this assessment. Native PostgreSQL search already serves the narrower promoted-memory search use case; it does not establish semantic-retrieval equivalence.

The current MVP prioritizes private Telegram conversation, remembered corrections and restart continuity. Watches and background responsibility are later ranked capabilities, not proof of an installed end-to-end watch system. The [current backlog][P-backlog] supersedes sequential delivery; the [controller hold][P-controller] and paused [CO change #217](https://github.com/danielnguyen/chat-orchestrator/pull/217) remain in force. No findings here waive privacy, owner authority, independent review, recovery or release checks.

## Current request and data boundaries

```text
Private Telegram adapter (contract and historical acceptance; live config unknown)
  -> CO POST /v1/chat -> orchestrate_chat
       -> BMS conversation lookup/create + canonical message append
       -> CR identity/continuation/containment/privacy decisions as configured
       -> BMS v2 retrieval bundle -> PostgreSQL records + Qdrant candidates
       -> CO prompt/model/output handling through LiteLLM
       -> BMS exact assistant message, trace and optional claim records
  <- CO answer/conversation identity -> adapter delivery

BMS compatibility /v1/chat and /v1/orchestrate/chat -> _run_chat
  -> independent retrieval/prompt/LiteLLM/assistant/trace pipeline

Read-only MCP adapter -> BMS promoted-memory search/debug -> PostgreSQL
```
